# NAPNE 360 — Matriz de aceite por prioridade de implementação

Data de elaboração: 2026-11-17.

Diagnóstico inicial preservado; consultar `verification.md` para as evidências posteriores de implementação desta entrega.

Base técnica: `main`, commit `13f7376cb18bdb8d0055b1a5bcbd4ace0b843417`, consultado na análise anterior desta conversa. A matriz transforma aqueles achados em verificações e organiza o trabalho em dez lotes; não representa nova execução do sistema nem homologação institucional.

Escopo registrado: RF01–RF14 e RNF01–RNF06, incluindo a administração prevista nos requisitos. RF15–RF19 permanecem excluídos. Emissão de documentos pedagógicos individuais não se confunde com relatórios gerenciais e dashboards excluídos.

Os critérios abaixo são propostas de aceite derivadas dos requisitos consolidados e dos achados. Prioridades são sugestões técnicas, sem responsáveis ou prazos atribuídos. Decisões de negócio ainda abertas estão identificadas como D01–D07; não foram presumidas como aprovadas.

## Como interpretar e registrar o aceite

| Campo | Significado |
| --- | --- |
| P0 | Prioridade sugerida para proteger acesso, dados e recuperação antes de uso com dados reais. |
| P1 | Prioridade sugerida para completar e comprovar os fluxos da entrega. |
| P2 | Prioridade sugerida para qualidade e escala, mantendo a exigência do requisito no contexto acordado. |
| L — Lacuna | Ausência ou integração incompleta identificada no código consultado; não implica reprodução em execução. |
| EP — Evidência parcial | Há implementação e/ou testes existentes, mas eles não demonstram todo o critério. |
| AV — A validar | Comportamento, risco ou qualidade ainda precisa de ensaio específico. |
| DI — Decisão institucional | Parte do critério depende de definição do NAPNE/IFAC ou do escopo final de entrega. |

Diagnóstico e aceite são campos diferentes. A matriz foi elaborada antes da implementação; seus diagnósticos abaixo registram esse ponto inicial. Execuções posteriores estão em `verification.md`. O aceite consolidado permanece pendente; os testes aprovados da CI continuam sendo evidências dos cenários que efetivamente cobriram.

Para cada CA, registrar: commit e ambiente; dados fictícios e pré-condições; procedimento ou comando; resultado esperado e observado; evidência; resultado (`aprovado`, `reprovado`, `não executado`, `bloqueado por decisão` ou `não aplicável com justificativa`); data e pessoa que validou. Evidências devem ser sanitizadas, sem dados reais, credenciais ou conteúdo restrito. A comprovação técnica não substitui a aprovação institucional quando ela for necessária.

## Condições propostas para o aceite da entrega

- Critérios aplicáveis executados no commit candidato, com evidência e resultado individual.
- Nenhum P0 aplicável reprovado ou sem verificação antes de uso com dados reais.
- Fluxos P1 da entrega demonstrados; mudança de escopo ou exceção identificada e explicitamente decidida, sem marcar requisito ausente como implementado.
- Critérios de escala e desempenho avaliados no contexto D07. Prioridade P2 não exclui requisito automaticamente.
- Documentação, CI e validação com usuários coerentes com o mesmo commit.
- Decisões D01–D07 resolvidas quando afetarem o aceite pretendido. Demonstração acadêmica e implantação institucional podem ter condições diferentes, que devem ficar explícitas.

## Evidências existentes e limites

Na análise anterior, a API e os logs do GitHub confirmaram o PR #1 integrado à `main` e a CI do commit `13f7376` concluída com sucesso. Os logs registraram 20 testes de backend, 1 teste Angular e 9 E2E, além de build/lint.
